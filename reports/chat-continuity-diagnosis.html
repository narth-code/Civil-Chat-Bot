Why conversations don't "continue"

Diagnosis from logs/api.log, .run/*.log and source, by 4 read-only subagents. No files were changed. The 2026-10-10 traffic is real; most of the earlier log is the pytest suite.

Bottom line. The backend does not lose chat ids. Conversation b6fe4cfc… was created 10-09 16:11, survived 3 server restarts, and accepted new turns on 10-10 at 01:55, 01:58 and 02:01. Continuity breaks in three separate places:
  1. UI forgets which chat you were in. activeId is useState(sampleId) and is never saved, so every reload opens the demo chat. Vite fires a full reload on each src/ edit, which makes this happen often.
  2. A chat dies permanently at 12,000 bytes of history. Seen live: f54a39a8… got HTTP 413 context_limit on its 5th turn at 01:40:58. History only grows, so every later send also fails.
  3. The agent has no memory of facts between turns. City, manual and regime are re-derived from the raw transcript each turn, and a few of those derivations are wrong for follow-ups.

2. Where continuity breaks

1 UI never saves the active chat id certain

  • src/ChatWorkspace.tsx:65 useState(sampleId); :78 the ref starts the same. No code writes it to localStorage, the URL or the server. The only localStorage uses in src/ are civil-theme (App.tsx) and the legacy-import keys.
  • Mount effect (:90-134) merges the server list into the sidebar but never calls selectChat. The detail-fetch effect returns early for sampleId, so no conversation loads until you click.
  • Also lost on reload: unsent drafts and the manual-scope selection. Switching Engineer ↔ Admin is not a cause: both workspaces stay mounted (App.tsx:96-104).
  • Smaller hazards: a reload between createChat and the create POST dropping the first typed message; each "New chat" click creating an empty server conversation immediately.

2 Hard 12,000-byte history wall; failed turns pollute history certain

  • app/services/turns.py:28,103-110: if json.dumps(history + new) exceeds MAX_REQUEST_BYTES, the turn is finished as context_limit with zero model calls and a 413. Nothing is trimmed (asserted intentionally by tests/test_routing_api.py:295-325).
  • _load_context (:322-334) loads every user row and every assistant_answer row, no limit. _finish (:431-441) writes origin="assistant_answer" for all outcomes, so FAILED_ANSWER_CONTENT, blocked, clarification and direct rows all go back into later history and the LLM sees the failure text as an assistant message. A 413 turn adds a user row plus a FAILED row, which makes the next turn worse.
  • Rough fit ([INFERENCE], live DB unreachable): ~2.1–3.3 KB per turn pair gives 3–5 turns. This matches 4 successes then 413.
  • A server restart during a pending turn converts it to a permanent interrupted FAILED row (mark_orphaned_runs, :122-130). There is no checkpointer, so an in-flight run cannot be resumed.

3. Options — pick what you want

Tick one or more per group, then use the bar at the bottom to copy your selection and paste it back to me. Sizes are estimates from the touchpoints, not measurements.

Group A — Remember the chat across reloads (fixes 1)

Group B — Stop long chats dying and keep failures out of history (fixes 2)

Group C — Make follow-ups actually continue the topic (fixes 3)

4. Suggested bundle

A1 + B1 + C1: no migration, no extra model calls, and it removes all three observed breaks. Add B4 if reload during a long turn bothers you. Defer C2 until you see city/manual drift survive C1.

Behavior changes would update README.md, and a new agent.py hash will register a new policy row. B1 and C1 each require rewriting or adding tests; C-group changes should be checked with eval/run.py on the live stack.

5. Not verified

  • Live DB was unreachable: the Docker daemon was down for every agent, so answer-length statistics and the message contents of b6fe4cfc / 14e8baa8 were not read.
  • Nothing was executed against the agent (no GPU/Ollama). Items marked [INFERENCE] are from code reading only, including the Dallas-override bug.
  • Slow turns (8–63 s): cause not established. Slow turns coincide with slow GET /api/routing-runs at the same instant, which hints at contention (shared GPU or event loop) rather than missing context. Not a continuity bug; worth a separate look.
  • No browser was driven; UI claims are static code reads plus log timing.
  • The 413 on f54a39a8 was attributed to accumulated history by arithmetic, not by reading the stored rows.
